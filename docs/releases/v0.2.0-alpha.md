# Sankofa v0.2.0-alpha

The web interface presents Sankofa as a scholarly archive with a search-first list, explicit metadata, citation exports, and inline thesis questions. The graph is a separate destination.

## Scope

The repository did not contain a frontend on `main` when this release was prepared. This release adds a React/TypeScript/Vite frontend. Every file under `src/sankofa/` remains unchanged, and the API stays on port 8001.

The interface uses serif titles, sans-serif body text, monospace IDs, light and dark design tokens, 4px borders, and 120ms colour/background transitions. It has no decorative gradients, shadows, glow, or navigation emoji. Missing scholarly metadata is explicit.

## Validation

`npm run build` checks TypeScript and bundles the interface. `npm test` exercises archive hydration, linked author metadata, filters, sorting, keyboard navigation, browser history, direct routes, questions, citation downloads, Oracle and Dream request contracts, streamed graph records, empty/error states, theme persistence, and narrow-screen layout.

Browser tests use fixtures matching the existing API and WebSocket response shapes. They are not a validation of live Neo4j/Qdrant/Ollama services or research outputs. The backend smoke test requires the configured local services.

Local validation: the production build and all seven browser tests passed. The existing Curator unit test passed. The complete existing backend test suite cannot collect because `tests/unit/substrate/test_event_store.py` imports a missing `sankofa.substrate.projections` module. This release leaves that backend issue unchanged.

The frontend workflow repeats the build and browser suite on GitHub. On the release branch, a successful run creates `v0.2.0-alpha` without overwriting an existing tag.

## Known limitations

The backend has no PDF download route and does not consistently store consent, licences, citation counts, or read counts. The frontend does not invent these values. Chat uses abstracts, and Oracle novelty/feasibility remain heuristic. The interface supports 500 records per search/list request; larger archives need backend pagination or batched APIs. A live sub-300ms load time has not been established.
